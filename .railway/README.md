# Service configuration

Install the pinned authoring dependencies with `npm ci --prefix .railway` and check the file with `npm run --prefix .railway typecheck` and `npm test --prefix .railway`. Railway IaC requires CLI 5.42.1 or newer. Link the project and environment (`railway link --project shuffify-v2 --environment production`) before running `railway config plan`; inspect the complete proposed change before applying it. [Production](../documentation/guides/production.md) describes what runs where, the backups and how to roll back.

The configuration declares the API, worker and Redis resources. Both application services require the owner-set shared `DATABASE_URL`; the API's pre-deploy migration receives that same variable. It is the direct, unpooled URL of the Neon project `shuffify-db`, branch `production`, so the worker can use PostgreSQL `LISTEN` and scheduler advisory locks. There is no SQLite fallback or database autoprovisioning in this Railway layout.

The configuration also keeps declaring the `postgres` resource that held these services' data before the move to Neon. No service references it, and a plan therefore never deletes it by omission. Retiring it is a deliberate step: evaluate the configuration with `SHUFFIFY_RAILWAY_RETIRE_POSTGRES=1`, after taking the final dump described in [Retiring the Railway PostgreSQL](../documentation/guides/production.md#retiring-the-railway-postgresql). Any other value of that input stops evaluation.

There is no staging environment. A new nonproduction environment needs its own Neon branch in `shuffify-db` (a backup branch is not staging) and must never use the production URL. Verify the branch identity from Neon metadata before any migration.

The split API also requires the owner-set shared `PUBLIC_ORIGIN`, `https://shuffify.app` in production. The private worker does not need `PUBLIC_ORIGIN`.

Both application services declare the same owner-selected GitHub repository and branch. Before running `railway config plan` or `railway config apply`, set `SHUFFIFY_RAILWAY_GITHUB_REPO` to the exact `owner/repository` slug and `SHUFFIFY_RAILWAY_GITHUB_BRANCH` to the exact branch name in the authoring shell; production uses `chrisrogers37/shuffify` and `main`. Both nonsecret inputs are required; missing, partial, or invalid inputs stop configuration evaluation. There is no default branch. These inputs are not container variables or shared credentials.

Use the same source inputs for planning and applying. To retain existing Git connections, use their currently connected repository and branch. Different values intentionally propose a source change; inspect that diff before applying. A separately connected source is not a substitute for declaring it in the managed configuration.

The worker starts one replica and uses its private control listener for health checks. Serving standby workers remain healthy without claiming scheduler leadership; authenticated control reports the actual memory scheduler leader and registrations separately. New Railway environments provide [IPv4 and IPv6 private addresses](https://docs.railway.com/networking/private-networking/how-it-works), so the configured IPv4 listener is reachable there. This configuration does not target older IPv6-only environments. Give only the API a public Railway domain. Vercel forwards browser API and authentication requests to that API.

Set these shared variable names in Railway before provisioning the services: `DATABASE_URL`, `PUBLIC_ORIGIN`, `SECRET_KEY`, `TOKEN_ENCRYPTION_KEY`, `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `SPOTIFY_REDIRECT_URI`, `WORKER_CONTROL_TOKEN`. Values remain in the platform. The configuration references them, the owner-set database and the Redis variables, and connects the API to the worker's private hostname. Keep both services in the same environment.

Each API deployment runs its pre-deploy command, which checks and upgrades the database before the new process starts; a failure blocks that deployment. Container startup never migrates. An empty development database first needs an explicit, one-time `flask create-schema` invocation with migration-process settings; upgrading never silently stamps an existing database.
